The leak behind most vibe-coded apps

Supabase lets the browser query your tables directly. That's safe only if every table has row-level security and the right rules. Miss one, and anyone with your public key can read the whole table. AI agents miss it all the time, and the people building with them often can't read the SQL to notice.

Svetra turns on row-level security for every table, closes each one by default, and refuses a table the API can reach without a rule (SVT001). Then it proves the rules hold on your real database.

How it works

A booking app with customers, staff at each location, and admins.

1. You and your agent write svetra.yaml 
roles:
  admin: { description: "Runs the business" }
  staff: { description: "Works at one location",
           scope: Location }

policies:
  customers_see_own:
    on: Booking
    allow: [select, insert]
    when: "customer == auth.user"
  staff_manage_local:
    on: Booking
    allow: [select, update]
    when: "has_role('staff', location)"
  admins_manage_all:
    on: Booking
    allow: [select, update, delete]
    when: "has_role('admin')"
2. svetra explain says it in plain English 
Bookings
  - Signed-in people can see and create a booking
    when its customer is them.
  - People with the staff role for a booking's
    location can see and change that booking.
  - People with the admin role can see, change
    and delete bookings.
  - Nobody can see bookings any other way.
3. svetra compile writes the rest 
create policy "staff_manage_local_update" on "public"."booking"
  for update to authenticated
  using ("svetra"."has_role"('staff', "location"))
  with check ("svetra"."has_role"('staff', "location"));
  • supabase/schemas/svetra.sql: tables, keys, indexes, row-level security, one policy per action, and a private roles table
  • src/svetra.gen.ts: TypeScript types and Zod validators. Money stays exact
  • supabase/tests/svetra.test.sql: access tests

Access tests: your database proves who can see what

The generated tests check every person, action and row on your database, signed in as each person and as a logged-out visitor, never with the service key that bypasses security. Run them with supabase test db.

Here, a migration adds one policy by hand that lets every signed-in person read every booking. Exactly the checks it breaks fail, each by name:

# Failed test 57: "alice can't see Booking b"
#         have: allowed
#         want: denied
# Failed test 64: "bob can't see Booking a"
#         have: allowed
#         want: denied
# Failed test 81: "staff at Location a can't see Booking b"
#         have: allowed
#         want: denied
# Looks like you failed 3 tests of 87
Result: FAIL
  • Every failure is reported, not just the first. Each check is undone afterwards, and the file rolls back, so nothing persists.
  • Expected results come from svetra.yaml, worked out by Svetra itself rather than copied from the SQL it wrote, so a hand-edited database or a compiler bug both show up.
  • Checked on PostgreSQL 16 in CI for every change to Svetra, and on a local Supabase stack with supabase test db.

What it checks before anything is written

svetra validate runs 21 checks, each with a stable code, a line and column, and a fix. A few of them:

CodeCatches
SVT001A table the API can reach with no access rule
SVT005Money stored as a float, which loses cents
SVT006A role that isn't declared, or a scoped role checked against the wrong thing
SVT007Logged-out visitors getting more than signed-in people
SVT008Weak or invalid sign-in settings, such as passwords shorter than 8 characters

Add --json and your agent gets the same findings in a form it can act on.

Install

macOS and Linux. The script checks the download's SHA-256 before installing.

curl -fsSL https://raw.githubusercontent.com/555aaditya/Svetra/main/install.sh | sh

Or with Rust:

cargo install svetra

Windows builds are on the releases page. Then:

svetra validate svetra.yaml
svetra compile svetra.yaml
svetra explain svetra.yaml
supabase test db

# Changelog

## Unreleased

- **Scheduled holes: `kind: schedule` runs a hole on the database's clock (milestone M4b, first part).** A hole with `schedule: "0 3 * * *"` (five-field cron, UTC, numbers, lists, ranges and steps) has no caller: it takes `reads`, `writes` and `grants` but not `input`, `output`, `as`, `when` or `audit` (`SVT020`, with a hint naming the keys each kind takes). It compiles to the usual role and body function plus a pg_cron job `svetra_<name>` that calls the body with `p_caller` null behind an advisory lock, and no function in `public` and nothing in `src/svetra.gen.ts`. Jobs named `svetra_%` that the design no longer declares are unscheduled. A bad expression is `SVT037` and `grants` on a schedule is `SVT040` (a warning). The generated tests check that no API role can run it, that the job exists once with the declared schedule, that no stale job is left and that the clock is UTC. `explain`, `context`, `view`, `diff` and `plan` say what starts it; changing a schedule is breaking. The Supabase stand-in has a stub `cron` schema. New example `jobs`. The pg_cron facts were checked on a local Supabase (docs/automations.md). Spec: `docs/format.md`, `docs/automations.md`.
- **A GitHub Action for `svetra plan`, and the flags it needs (milestone M6).** `uses: 555aaditya/Svetra@<tag>` on a pull request that changes `svetra.yaml` posts one comment, edited in place on every push, with each change classified and who gains or loses access in plain words; the check fails while a destructive change or wider access has no yes in `accept`, and the plan also goes to the job summary, so a fork's read-only token still shows it. New on `plan`: `--from-git REF` (also on `diff`) reads the old design from a git ref such as the PR's base, `--no-write` never writes the rename migration (CI must not write into the checkout), and `--markdown` prints the comment. Run it with `pull_request`, never `pull_request_target`. The Action needs a release that has these flags, so pin a version from the next release on. Spec: `docs/action.md`; `docs/change.md`.

## 0.8.3 (2026-11-22)

A pre-launch checklist (`svetra doctor`), `infer` that follows real apps (profile tables, `on delete`, role checks) and can check its draft against a copy of the database, `audit: true` on entities and holes, and two fixes to the generated tests found by studying an app written by others.

- **`svetra doctor` reads a database: `--db URL`, `--local` or `--migrations [DIR] [--scratch URL] [--strict]`.** It runs `check` on the source and shows its findings unchanged under "Data exposure" (area `data` in `--json`, with the database object and no file), next to the folder checks, and adds `schema_not_in_git` (a warning when the database has tables but no `.sql` file under `supabase/migrations/` or `supabase/schemas/` is tracked by git). A critical finding in either group exits `1`; an unreachable database, no Docker, or (with `--strict`) a failed migration exits `2`. Migrations that fail to apply are listed and put "Database" under "Not checked". It still never says the project is ready: auth settings and storage buckets are not read yet. Spec: `docs/doctor.md`.
- **`svetra doctor [DIR] [--json]`: the pre-launch checklist, first part (the project folder).** It reads the folder and reports leaked keys: a service role key (a JWT whose decoded `role` is `service_role`, or an `sb_secret_` key) in front-end code or any tracked file, other secrets by format (Stripe, AWS, GitHub, Supabase access tokens, private keys), a JWT secret or a database password in code, a committed `.env`, a `.env` that is neither committed nor ignored, a literal secret in `supabase/config.toml`, and a signed token with an unrecognised role. The anon and publishable keys are never flagged, and a key is judged by what it decodes to, never by its variable name. It also runs `compile --check` as a warning per out-of-date generated file, and lists backup reminders. It never prints a secret's value, makes no network call and writes nothing; exit `1` on a critical finding, `2` for a usage error. It never says the project is ready: the database isn't read yet (data exposure, auth settings and buckets are the next parts), and that is stated on its first and last lines. Spec: `docs/doctor.md`.
- **`audit: true` on an entity or a hole records who did what (milestone M4d).** On an entity, every insert, update and delete of a row goes to one append-only table, `svetra.audit_log`, with the person (`auth.uid()`), the time, and the row before and after, whoever makes the change: the API, a hole body or SQL by hand. On a hole, each call that runs is recorded with the caller and its inputs, by the generated wrapper, so the hole's own role never touches the log. The log is closed to the app (row-level security with no policy, no grants, an unexposed schema) and a trigger refuses `update`, `delete` and `truncate` for every role, including its owner. It is tamper-evident, not tamper-proof: a superuser can drop the trigger. A call the `when` guard refuses can't be logged, because the refusal rolls the transaction back; reads, retention and export are not part of this. A file with no `audit: true` compiles to the same SQL as before. `diff` and `plan` list `add_audit` and `remove_audit`, `explain` and `context` show it, and the JSON Schema has the new key. New example `audited`, checked on PostgreSQL 16. Spec: `docs/format.md` (Audit), `docs/compiler.md`.
- **`svetra infer` follows a profile table, `on delete`, and `auth.role()`; untranslated policies say why.** A table whose `uuid` primary key references `auth.users(id)` is a profile table: that key becomes `{type: user, primary: true}`, and a column that references it becomes a `user` field, so `auth.uid() = author` translates. The column's foreign key goes from the profile table to `auth.users`, which accepts a person with no profile row; the draft says so in a `# lossy` note (that is looser data integrity, not wider access). A foreign key's `on delete cascade` becomes `on_delete: cascade`, and `set null` becomes `set_null` when the column isn't required; `set default`, other `on update` actions, and `set null` on a required field stay as notes. `auth.role() = 'authenticated'` is read as the policy's `as` (for each role the `to` covers, the roles it is false for are dropped, and the rest must agree). `auth.role() = 'anon'` and other values stay untranslated: a request with no JWT runs as `anon` with a null `auth.role()`, so `as: anon` would be wider than the database. Each `# UNTRANSLATED policy` now names its cause (a reference, a function call, a JWT claim, a subquery, ...), not one fixed sentence. The draft is never wider than the database, with one stated caveat for a request with no JWT as `anon` (docs/infer.md). On the Supabase Slack clone, 10 of 14 policies now translate, up from 0 (`study/p7/outside/infer`). The throwaway Supabase database used by `--check-draft` now has `auth.role()` read the claims, as current Supabase does. Spec: `docs/infer.md`.
- **Generated tests now catch a takeover of a `user`-keyed row.** On an entity whose primary key is a `user` field (a profile table keyed by the person), a loosened update rule (`using (true)` or `with check (true)`) let a person with no profile take over someone else's by changing its key to their own id, or hand theirs to a person who has none, and the tests missed it because the old change-who-owns checks could only aim at keys already stored. Each signed-in person now also tries to set the key of each stored row to a key nobody holds: themselves when they hold no row, and the fourth person. Other entities are unchanged. Spec: `docs/compiler.md`.
- **`svetra infer --check-draft FILE`: check that a draft means what the database does.** It compiles the draft, seeds the draft's test world into a throwaway copy of the original database, runs the generated access tests, and lists each check where the draft and the database disagree, in plain words and grouped by entity. The copy is built from `--migrations [DIR]` (as `check --migrations` does) or from a schema-only `pg_dump` of `--db`/`--local`, so the original is only read and no `--scratch` is needed. An entity with an untranslated policy is skipped (the draft is narrower there on purpose), and so is one whose test rows the database refuses, with the database's own message. Exit `0` all agree, `1` a disagreement, `2` it couldn't run. It runs in Supabase's own database image (`public.ecr.aws/supabase/postgres`, pinned), which ships pgTAP, so nothing is installed at run time; if the image is missing it prints the one `docker pull` to run. Spec: `docs/infer.md`, Differential testing.
- **`on_delete` on `ref` fields: `restrict` (default), `cascade` or `set_null`.** It compiles into the foreign key. The generated delete checks now expect a delete the rules allow to be `blocked` (SQLSTATE 23503) while a `restrict` reference still points at the row, through any cascades, worked out from the spec and not from the keys; before, such a check on a referenced row failed on an unmodified app. `diff` and `plan` report a changed `on_delete` (`cascade` is breaking). `on_delete` on any other type, an unknown value, or `set_null` on a required field is `SVT023`. New example `forum`. Spec: `docs/format.md`.
- **`svetra infer` drafts policies: the owner column, `true`, and restrictive ones (milestone 2).** A database policy becomes one Svetra policy in a top-level `policies:` section when its condition is `true` or an owner check on a `user` field (`auth.uid() = col`, `(select auth.uid()) = col`, `col = auth.uid()`, with matching `::text` casts on both sides, joined by `AND`/`OR`): `when: "col == auth.user"`, with `allow` from the command (`ALL` is all four), `when`/`check` from `using`/`with check`, `restrictive: true`, and `as` from the roles. Everything else (subqueries, membership tables, jwt claims, functions) stays an `# UNTRANSLATED policy` comment with the rebuilt `CREATE POLICY`. **The draft is never wider than the database:** an action the role has no table privilege for is dropped, a restrictive policy that doesn't translate removes every policy of its table, an entity with only some policies translated says the draft is NARROWER, and `private: true` now appears only on an entity with no translated policy. A table with row-level security off stays private with a comment, and no policy is invented. Spec: `docs/infer.md`, Policies.
- **A `user`-typed primary key now works with the generated access tests.** A profile table keyed by the auth user's id made the insert checks collide with the row the tests had already stored for that person, so an unmodified app failed its own tests. On such an entity the four test rows are now keyed by four different people (alice, bob, carol and a fourth who has no checks), so creating `c` can only be allowed for carol and `d` for nobody. Other entities and `user` fields are unchanged. New example `profiles`. Spec: `docs/compiler.md`.

## 0.8.2 (2026-11-21)

Check what your migrations build with no live database, draft a `svetra.yaml` from an existing one, start from a template, and generated tests that catch a class of gap the mutation study had missed.

- **The generated access tests also try an owner who holds a role, and owner and reference changed together.** A Z3 model of the bookings policies found four mutants the study had wrongly judged harmless: with two update policies on one table, loosening one lets the other's people through, because PostgreSQL ORs the update policies' `with check` conditions independently. The tests missed them for two reasons: no person was both an owner and a role holder, and no update changed a `user` field and a `ref` field at once. Now `alice who is also <role>` (the role is granted by the database owner just before each of her checks and undone with it, so it never changes any other check) and one update per person and row that takes a row over and moves it. Only apps with a `user` field and roles get the new person. Bookings goes from 124 to 178 checks. The other examples with roles grow similarly, and an app without roles only changes the helper's signature.
- **The P7 study data is corrected and extended** (`study/p7`). A Z3 model of the bookings policies disagreed with the study's classification of four survivors, and each was confirmed on PostgreSQL 16 to be a real gap: with two update policies on one table, loosening one lets the other's people through. Round 1 has 13 real gaps, not 9; round 2 has 4, not 0. Round 3 (this release's generator), on the stand-in and on a real Supabase with identical results, catches 147 of 147 mutants that change access. The Z3 model, its PostgreSQL check and a comparison of the 23 operators with faults found in public repos are in `study/p7`.

- **`svetra check --migrations [DIR]`: check what your migrations build, with no live database.** It applies `supabase/migrations` (or `DIR`) in file-name order to a throwaway PostgreSQL 16 in Docker (no network, no extra privileges, removed afterwards, or stopping itself after 15 minutes if interrupted), with a stand-in for Supabase, then runs the usual checks. A migration that fails is rolled back whole and the others still run; the report lists each failure (file name and the database's first error line, never the SQL) and says this reads migrations, not the live database. `--strict` exits 2 on any failure, `--scratch URL` uses an empty database you provide instead of Docker (a fresh `supabase start` database makes it a check on real Supabase), and `--json` adds a `migrations` object. The Supabase stand-in moved to `src/standin/` so the binary, the access-test scripts and the leak study share it. Spec: `docs/check.md`.
- **`svetra view` shows which fields a change may touch.** A Change cell covered by an update rule with `only` now says so in the detail panel and in `--json` (`only`: the fields, the sentence "They can change only its status." and the rule), in the words `explain` uses.

- **`svetra mcp` has a `check` tool: ask an agent "what is open in this database or these migrations?"** It takes exactly one of `db`, `local`, `snapshot` or `migrations` (a folder, or `true` for `supabase/migrations`), with `scratch` and `strict` for migrations and `schemas` (default `["public"]`), and returns the JSON of `svetra check --json` plus a one-sentence `summary`. Findings are results, not errors; a call that can't run, or `strict` with a failed migration, is a tool error. Connection passwords are never returned. The CLI and the tool now share one function for reading the source. Spec: `docs/agents.md`.
- **`diff` and `plan` now compare column rules.** Removing `only` from a policy, or adding a field to its `only` list, is reported as wider access and `plan` refuses it until `--accept wider_access`; gaining `only` or removing a field is reported as narrower. Before, any change to `only` was listed as a safe "change rule" with no access line.
- **`svetra new <template> [DIR]` starts a project from a template.** Five small, commented designs ship in the binary: `notes`, `blog`, `bookings`, `teams` and `approvals`. `svetra new --list` describes them in plain English. It writes only `svetra.yaml`, never replaces an existing one (exit 2), and suggests `explain`, `compile` and `init` as next steps. Spec: `docs/new.md`.
Draft a `svetra.yaml` from a database you already have: `svetra infer`, milestone 1 (entities and fields, no policies).

- **`svetra infer (--db URL | --local | --snapshot FILE) [--out FILE] [--force]`** reads the catalogs like `check` and writes a draft: one entity per table in `public` (PascalCase of the table name, so it compiles back to the same table), fields with exact or noted-as-widened types, `ref` and `user` for foreign keys, `unique`, `indexes`, and the check constraints that translate. Everything it can't translate stays a `# UNTRANSLATED` comment with the original SQL, never dropped or loosened. `check`'s findings go in as comments. Entities are `private: true` until policies are written (milestone 2). It refuses to overwrite a file without `--force`.
- **The infer query adds four snapshot keys** (`columns`, `constraints`, `indexes`, `enums`); `check`'s query and findings are unchanged. Spec: `docs/infer.md`.

## 0.8.1 (2026-11-20)

Fewer false alarms from `svetra check`, found by auditing it on 300 public Supabase repos.

- **`check` explains a policy written for the backend.** When an open policy's name says service role, system or backend and it has no `to service_role`, the finding now says so ("it applies to everyone") and the fix is to delete it, since the service role skips row-level security, or add `to service_role`. Kind and severity are unchanged. It was the most common real open write in the leak-study audit.
- **`check` no longer calls an open insert a critical write.** A permissive `INSERT` policy for `anon` or `public` with a check of `true` lets people add rows, not change existing ones, and is often a sign-up or contact form. It is now a warning, `open_insert` ("Anyone on the internet can add rows to ..."). `open_write` (critical) is now only an open `UPDATE`, `DELETE` or `ALL`. An open insert for signed-in people is ordinary and no longer reported as `signed_in_write`. Found by hand-auditing 30 findings from a study of public Supabase repos: about half of the `open_write` criticals were insert-only.

## 0.8.0 (2026-11-18)

Say what an update may turn a row into, so a state change isn't a hole: `check` on update, and `restrictive` policies.

- **A policy can say which fields an update may change: `only`.** `only: [status]` on a reviewer's policy lets them approve or reject a document and change nothing else, so "approve and retitle in one update" is refused. It is an allow-list, so a column added later stays locked. Svetra generates a guard trigger (the part row-level security can't do, because a policy never sees the old and new row together), refuses with the same error as any policy, and **the access tests prove it on your database**, including the case only the guard can refuse: a locked field changed beside a status change the rules allow. The service role, the owner and custom code are exempt, as they are from row-level security. In the agent evaluation, all four agents given the approvals app wrote this trigger by hand, outside the design; it is now one line. New codes **SVT035** and **SVT036** (a field limited by one policy but freed by another that covers the same person). `explain` says "They can change only its status."
- **A policy can say what an update turns a row into: `check`.** `when` is the row as it is, `check` is the row afterwards (PostgreSQL's `USING` and `WITH CHECK`), so "a draft becomes submitted, a submitted document is approved or rejected, and nothing else" is a policy, not a hand-written function. Without a `check` nothing changes. The access tests try each value a rule with a `check` reads (each enum value, or true and false), so the transitions are proven on your database like the rest. In the agent evaluation, an agent given this exact app wrote four holes; the example (`approvals`) now needs none.
- **`restrictive: true`:** a policy that must hold in addition to a permissive one, compiled to `as restrictive`. "Suspended people can't write" is one rule, not an edit to every policy. `explain` ends each sentence it narrows with "and only when ...". New code **SVT033** (a `check` on a policy that doesn't allow update).
- **`validate` warns when two policies combine into an update neither allows alone (SVT034).** PostgreSQL combines the old-row and new-row conditions independently across policies, so a row can pass one policy's `when` and another's `check`. It found a real flaw in the first draft of the approvals example (a reviewer could make themselves the author), fixed with a constraint.
- **In the test world, a second `user` field points at the other person,** so a rule that compares two people (an author and a reviewer) sees two different ones. No existing example has two `user` fields, so none of their tests change.
- **`compile` refuses a hole body that would break the function around it.** Svetra writes the `begin` and `end` around a hole's hand-written body, so the body must be statements ending in `;`. A body that is a whole function (`begin … end` with no `;` after it) left a stray `end` and a migration that didn't parse; an agent did exactly that in the agent evaluation, with no database to find out. It is now **SVT032**, reported against `supabase/holes/<name>.sql` (over MCP too, as `hole_bodies`), with nothing written. Nested blocks ending in `end;`, trailing comments and empty bodies are still fine. The skill and the agents doc say bodies are statements only.
## 0.7.0 (2026-11-16)

Find the leaks in an app you already have: `svetra check`.

- **`svetra check`: find the leaks in an app you already have.** Point it at any Supabase or PostgreSQL database (`--db URL`, or `--local` for `supabase start`) and it reports, in plain English, where data is open to people who shouldn't reach it: tables with row-level security off, policies that let anyone read or change every row, views and functions that skip row-level security, and rules that trust `user_metadata`. Each finding has a fix. It needs no `svetra.yaml`, runs one read-only query, never prints the password, and exits 1 on a critical finding, so it works in CI. Without `psql`, `--print-query` gives the query to run in the Supabase SQL editor, and `--snapshot` reads its result.
## 0.6.0 (2026-11-16)

Change safely: `svetra diff` and `svetra plan` say what a change does to the data and to who can see what, before it reaches the database.

- **Citable:** a `CITATION.cff`, and every release from now on is archived on Zenodo with a DOI.
- **Safe change: `svetra diff` and `svetra plan`.** They compare `svetra.yaml` with the design the database has (by default, the version committed in git `HEAD`; or `--from`) and classify every change: **safe**, **breaking** (existing rows or app code may fail, such as a new required field with no default) or **destructive** (data is deleted, such as removing a field). They also say whose access widens or narrows, person by person, from the same evaluator as the access tests: "A signed-in person who owns nothing can now see all customers (was: none)." `plan` exits 1 on destructive changes and wider access until they're accepted with `--accept`.
- **Renames keep the data.** Declare one with `was: <old name>` on an entity or field. `plan` writes the `alter ... rename` migration to run before `supabase db diff`, which would otherwise drop the column and add an empty one. An undeclared rename is reported as destructive, with a hint to add `was`. New codes: SVT030 (a `was` that can't be a rename) and SVT031 (a rename that's already applied).
- **Agents:** a read-only `plan` tool in `svetra mcp`, and a skill step: show the person every destructive and wider line, and get their yes before `--accept`.

## 0.5.0 (2026-11-16)

See who can see what: `svetra view`, clearer `explain`, and every release now tested on a real Supabase.

- **Tested on a real Supabase:** CI now runs every example's access tests and deliberate breakages on a real local Supabase, not only on PostgreSQL with a stand-in. That's the check that found the 0.4.2 security bug.
- **`explain` reads fields named for an action as that action:** `paid_by == auth.user` is now "it was paid by them", not "its paid by is them", and `assigned_to` reads "it is assigned to them".
- **`svetra view`: who can see and change what, as one page.** A table of every person (signed out, two signed-in people, one who owns nothing, each role) by every thing and action, answered All, Some or No in words. Select a cell to see which rows the tests tried, the `explain` sentences that allow or rule it out, and the access test numbers that check it. A question box answers "who can see orders?" directly, and the page also shows custom code, a diagram of the links, and sign-in notes. The answers come from the access tests' own evaluator, so the page and the tests can't disagree, and a test checks every cell against the generated test file. It's one self-contained HTML file (`.svetra/view.html`, added to `.gitignore`) with no network access; `--json` prints the view model instead.

## 0.4.2 (2026-11-16)

A security fix for holes, and holes that can give people roles.

- **Security fix: logged-out visitors could call holes meant for signed-in people,** on a real Supabase. Supabase grants execute on every new function in `public` to `anon` directly, and the generated `revoke ... from public` left that grant in place. A hole with a `when` guard still refused them, but a hole without one, such as `write_audit` in the posts example, ran for anyone. Both hole functions now revoke execute from `anon` and `authenticated` by name before granting it to the hole's `as` roles. **Recompile and apply the schema.** The CI stand-in for Supabase now has the same default privileges, so this is checked on every PR; the generated access test `anon can't call <hole>` caught it on a real Supabase.
- **Holes can give people roles,** so people can start a team and invite others. A hole with `grants: [member]` may add and remove grants of the roles it lists, and no other: a row-level security policy on `svetra.role_grants` keeps every other role, such as `admin`, out of its reach. An undeclared role in `grants` is SVT006. `explain`, `context` and `graph` show what each hole can give.
- **Access tests prove it:** each hole's role has privileges on role grants only if it has `grants`, and it can give exactly the roles it lists. A new example app, `teams`, starts teams and adds members through two such holes, and a deliberately widened policy fails exactly one check.

## 0.4.1 (2026-11-13)

Stronger access tests, found by a mutation study, and fixes from running Svetra inside Claude Code.

- **Stronger access tests, found by a mutation study.** `scripts/mutate.py` breaks the deployed database in 197 ways (policies dropped, widened or moved to another role, row-level security off, extra policies, weakened role checks and hole guards, extra grants) and counts what the generated tests catch. They now also check:
  - **carol,** a signed-in person with a second factor who owns nothing and holds no role, so a rule open to every signed-in person, or a role check that forgets who holds the role, fails a check;
  - **changing who owns a row or what it belongs to:** each signed-in person tries to set a row's `user` fields to themselves and point its `ref` fields at another row, and the rule must hold on the row as the update leaves it;
  - **holes:** only the declared callers can run a hole's public function, and nobody can run the function inside `svetra_holes` directly, where the caller's id could be forged;
  - **roles:** alice can't grant herself a role.

  Recompile to get the new checks. The bookings example goes from 87 to 124 tests.
- **`graph` and `context` draw a design that's complete but unsafe.** When the only errors are a table with no rule (SVT001) or money as `float` (SVT005), they still print their output, with the diagnostics on stderr and exit 1; over MCP, the output plus a `diagnostics` list. An agent fixing those errors can see the design instead of drawing it by hand. `explain` still refuses any file with errors.
- **The Claude Code skill re-runs `explain`** before answering "who can see X?", instead of answering from an earlier call.
- **Setup behind a company proxy** is documented: set `NODE_EXTRA_CA_CERTS` to the proxy's root certificate before `npx svetra`, and where the agent is started from, since the MCP server downloads the same way.

## 0.4.0 (2026-11-07)

Svetra inside your agent: holes for custom code, an MCP server, and a Claude Code skill.

- **`svetra init`** sets a project up for agents: the Svetra skill for Claude Code (`.claude/skills/svetra/SKILL.md`), which teaches the design-validate-compile-explain loop and its safety rules; the `svetra` server in `.mcp.json`, keeping every other server; and a starter `svetra.yaml` if there isn't one.
- **`svetra mcp`**, an MCP server over stdio for Claude Code, Cursor, Codex and other agents. Its tools are `validate`, `compile` (with `check`), `explain`, `context` and `graph`, each returning JSON; an invalid file returns its diagnostics with remediation hints. Add it to Claude Code with `claude mcp add svetra -- npx -y svetra mcp`.
- **Holes run as guarded Postgres functions.** A hole like `transfer` compiles to a function the app calls with `supabase.rpc()`. It runs as its own database role, granted only the tables in its `reads` and `writes`. A new `when` condition, such as `source.owner == auth.user`, is checked before any hand-written code and refuses everyone else with SQLSTATE 42501, and a new `as` says who may call it. The body is PL/pgSQL in `supabase/holes/<name>.sql`, created once as a stub and never overwritten. `src/svetra.gen.ts` gets a typed function per hole that validates input and output with Zod.
- **Access tests cover holes:** each hole's role must hold exactly its declared table privileges, and its guard is checked for every person. `explain` says who can call each hole, in plain words.
- **npm package.** `npx svetra` runs the release binary for macOS, Linux or Windows: the first run downloads it from the matching GitHub release, checks its SHA-256 against `SHA256SUMS`, and caches it. No dependencies and no install scripts.

## 0.3.0 (2026-11-05)

Sign-in settings: how people get in, safe by default.

- **Sign-in settings.** A new `auth` section: `sign_in` (email and OAuth providers), `signup` (`open` or `invite_only`), `confirm_email` and `password` rules, with safe defaults (10-character passwords, confirmed emails). `svetra compile` sets only the keys Svetra owns in `supabase/config.toml`, keeping every other line, and `--check` names each key that differs. OAuth secrets are written as `env(...)` references.
- **Second factors for roles.** `mfa: true` on a role makes `has_role` require an `aal2` session. The access tests add a person who holds the role without a second factor and must get nothing extra.
- **`explain`** adds "Signing in" and "Before going live". `context` adds an `auth` line.
- **New checks:** `SVT008` (invalid sign-in settings) and `SVT009` (info: no `auth` section, so Supabase's weak defaults apply).

## 0.2.0 (2026-11-04)

Access tests: your database proves who can see what.

- **Access tests.** `svetra compile` also writes `supabase/tests/svetra.test.sql`, run with `supabase test db`. It checks every person × action × row as real users (`anon` and signed-in, never the service key), with expected results evaluated from `svetra.yaml` rather than the generated SQL. It catches drift, such as a migration adding a permissive policy or turning row-level security off, and reports every failing check, not just the first.
- **Checked on a real local Supabase** (Postgres 17) with `supabase test db`: all 87 bookings checks pass, and a policy added by hand that lets everyone read bookings fails exactly the three checks it breaks. CI runs the same check on PostgreSQL 16 for every PR.

## 0.1.0 (2026-11-04)

The first release. Svetra reads a `svetra.yaml`, checks it, compiles it for Supabase, and explains it.

**Commands**
- `svetra validate [FILE] [--json]` runs 19 checks with stable codes, positions and fixes. Among them:
  - an exposed table with no access rule (SVT001)
  - money stored as float (SVT005)
  - role mistakes (SVT006)
  - logged-out visitors getting more access than signed-in people (SVT007)
  - expressions that don't type-check (SVT003)
- `svetra compile [FILE] [--check]` writes two files:
  - `supabase/schemas/svetra.sql`: tables, constraints, foreign keys, indexes, row-level security on every table, policies, and roles;
  - `src/svetra.gen.ts`: Zod validators and TypeScript types, with exact decimals.

  `--check` fails if either file is stale or hand-edited.
- `svetra explain [FILE]` describes the app in plain English: what's stored, the rules, and who can see and change what.
- `svetra graph [FILE]` draws a Mermaid diagram of entities, links, access, roles and custom code.
- `svetra context [FILE]` gives the whole app in about half the yaml's size, for agents.

**The format** (`docs/format.md`):
- entities, fields and 13 types
- constraints and policies, with `as: authenticated`, `anyone` or `anon`
- holes
- roles: global, or scoped to rows of one entity, with `has_role()`

**Verified:** every change applies the generated SQL to PostgreSQL 16 and reads back after every write, as every role.

# `svetra compile`, version 0.1

This document specifies what the compiler produces from a valid `svetra.yaml`. The format itself is specified in [`format.md`](format.md). When the compiler and this document disagree, that's a bug in one of them.

## Command

```sh
svetra compile [FILE] [--check]
```

- **`FILE`** defaults to `./svetra.yaml`. Paths in the output are relative to the folder `FILE` is in.
- **The compiler validates first.** If `svetra validate` would report any error, nothing is written, and the diagnostics are printed with exit code `1`.
- **`--check`** writes nothing. It exits `0` if every output file already matches what the compiler would write, and `1` otherwise, listing the files that differ. CI uses it to catch hand edits and stale output.
- **Exit codes:**
  - `0`: written, or up to date with `--check`
  - `1`: validation errors, or stale files with `--check`
  - `2`: usage error

## Outputs

| File | Contents | Consumed by |
|---|---|---|
| `supabase/schemas/svetra.sql` | Tables, constraints, foreign keys, indexes, row-level security and policies | Supabase's [declarative schemas](https://supabase.com/docs/guides/local-development/declarative-database-schemas): `supabase db diff` turns it into migrations |
| `src/svetra.gen.ts` | TypeScript types and Zod validators, one per entity | The React app |
| `supabase/config.toml` | Only the sign-in settings Svetra owns, edited in place (see [Sign-in settings](#sign-in-settings)). Only with an `auth` section | `supabase start` locally. `supabase config push` sends them to a hosted project, and `supabase config diff` previews that |
| `supabase/holes/<name>.sql` | A stub body for each hole, created only if the file doesn't exist. **Never overwritten:** it's yours | You or your agent write the body |
| `supabase/tests/svetra.test.sql` | Access tests: every person × action × row, checked as real users (see [Access tests](#access-tests)) | `supabase test db`, which runs it with [pgTAP](https://pgtap.org) |

Version 0.1 doesn't make these paths configurable.

**Every file starts with this header:**

```
-- Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.
```

It's `//` instead of `--` in TypeScript. The **revision** is the first 12 hex digits of the SHA-256 of the `svetra.yaml` bytes. `svetra check` will later use it to spot generated files that are older than the graph.

## Determinism

The same `svetra.yaml` and the same compiler version always produce byte-identical files:
- Output order is fixed: the sections below appear in order, and entities and policies within a section appear in file order.
- No timestamps, no randomness, and no hash-map iteration order.
- Files end with a single newline.

## SQL

### Names

- **Every identifier is double-quoted.** Entity names such as `Order` and `User` become reserved words in SQL (`order`, `user`), and quoting makes them safe.
- **The table name is the entity name in snake_case,** in the `public` schema: `LedgerEntry` becomes `"public"."ledger_entry"`.
- **Column names are the field names.**
- **Generated constraint and index names:**

| Object | Name |
|---|---|
| Enum check | `<table>_<field>_values` |
| Declared constraint | its own name, from `constraints` |
| Unique constraint | `<table>_<col>_<col>_key` |
| Foreign key | `<table>_<field>_fkey` |
| Index | `<table>_<col>_<col>_idx` |

### Sections, in order

1. **Tables.** `create table` for every entity: columns, primary key, `not null`, defaults, enum checks, declared constraints and unique constraints. No foreign keys here.
2. **Foreign keys.** `alter table ... add constraint ... foreign key` for every `ref` and `user` field. Adding them after the tables means entities that reference each other in a cycle still work.
3. **Indexes.** Declared `indexes`, plus one index for each reference field that no index or unique constraint already leads with (rule SVT010).
4. **Access.**
   - `alter table ... enable row level security` for **every** table, so a table with no policy denies everyone.
   - For `private` entities, also `revoke all ... from anon, authenticated`, so the generated API can't reach them at all.
5. **Policies.** One `create policy` for each policy and action.

When any entity or hole has `audit: true`, an **Audit** section follows Guards (see [Audit](#audit)).

When the file declares `roles`, a **Roles** section comes before Access:

```sql
create schema if not exists "svetra";
create table "svetra"."role_grants" (
  "user_id" uuid not null references "auth"."users" ("id") on delete cascade,
  "role" text not null check ("role" in ('admin', 'staff')),
  "scope_id" uuid,
  constraint "role_grants_key" unique nulls not distinct ("user_id", "role", "scope_id")
);
alter table "svetra"."role_grants" enable row level security;

create function "svetra"."has_role"(p_role text, p_scope uuid default null)
  returns boolean language sql stable security definer set search_path = ''
  as $$ select exists (
    select 1 from "svetra"."role_grants" g
    where g."user_id" = (select auth.uid()) and g."role" = p_role and g."scope_id" is not distinct from p_scope
  ) $$;
revoke all on function "svetra"."has_role"(text, uuid) from public;
grant usage on schema "svetra" to anon, authenticated;
grant execute on function "svetra"."has_role"(text, uuid) to anon, authenticated;
```

- **`role_grants` is unreachable from the API.** The `svetra` schema isn't exposed by Supabase, the table has no grants for `anon` or `authenticated`, and it has row-level security with no policies.
- **`has_role` is `security definer`:** it reads `role_grants` as its owner. A policy calling it never runs another table's policies, which avoids the recursion problem that policies referencing each other can cause. `search_path` is fixed to `''`, so it can't be hijacked.
- `unique nulls not distinct` needs PostgreSQL 15 or later, which Supabase uses.

### Columns

| Field | Column |
|---|---|
| `primary: true` with `uuid` | `uuid primary key default gen_random_uuid()` |
| `primary: true` with another type | `<type> primary key` |
| `required: true` | `not null` |
| `default: x` | `default <literal>` |
| `auto: now` | `default now()` |
| `enum` | `text`, plus `constraint "<table>_<field>_values" check ("<field>" in ('a', 'b'))` |
| `ref` | `uuid`, plus a foreign key to the referenced entity's primary field, with the field's `on_delete` |
| `user` | `uuid`, plus a foreign key to `"auth"."users" ("id")` |

The other type mappings are in [`format.md`](format.md#types).

Foreign keys on `ref` fields follow the field's `on_delete` ([format.md](format.md#deleting-a-referenced-row)): `restrict`, the default, writes nothing and gets PostgreSQL's `on delete no action`, so a referenced row can't be deleted while something still points at it; `cascade` appends ` on delete cascade` and `set_null` appends ` on delete set null`. A `user` field's key to `auth.users` always has the default.

### Expressions in SQL

Constraints and policy conditions translate like this:

| Expression | SQL |
|---|---|
| `a == b`, `a != b` | `a = b`, `a <> b` |
| `x == null`, `x != null` | `x is null`, `x is not null` |
| `and`, `or`, `not` | `and`, `or`, `not`, with parentheses kept |
| `x in ['a', 'b']` | `x in ('a', 'b')` |
| `'it''s'` | `'it''s'`; single quotes are escaped by doubling |
| A field `f` | `"f"` |
| `auth.user` | `(select auth.uid())`, the form Supabase recommends, which Postgres evaluates once per query instead of once per row |
| `has_role('admin')` | `(select "svetra"."has_role"('admin'))`, evaluated once per query |
| `has_role('staff', location)` | `"svetra"."has_role"('staff', "location")`, evaluated per row |
| `ref.field` (policies only) | `(select t."field" from "public"."<target>" t where t."<pk>" = "<table>"."ref")`, a scalar subquery on the referenced row's primary key |

### Guards

For an entity with any `only`, the schema has a `-- Guards` section after `-- Policies`: a `before update` row trigger, `svetra_guard`, and its function, `svetra.guard_<table>`. For each field that some update policy's `only` leaves out, it refuses (SQLSTATE `42501`) an update **through the API** (`current_user` is `anon` or `authenticated`) that changes the field when the person is covered by no permissive update policy that frees it, or by a restrictive one that doesn't. A policy covers the person when its role matches and its `when` holds on `old`; a null counts as not covering. The service role, the table owner and hole bodies aren't `anon` or `authenticated`, so they are exempt, as they are from row-level security. The full rules are in [column-rules.md](column-rules.md).

### Policies

An update policy compiles to `using (<when>) with check (<check>)`, where `<check>` is the policy's `check`, or `<when>` when it has none. A `restrictive: true` policy compiles to `create policy ... as restrictive`.

- `select` and `delete` put the condition in `using (...)`.
- `insert` puts it in `with check (...)`.
- `update` puts it in both.
- A policy with one action keeps its name. With more than one action, each gets `<policy>_<action>`.
- The default becomes `to authenticated`. `as: anyone` becomes `to anon, authenticated`, and `as: anon` becomes `to anon`. In Supabase, signed-in people run as `authenticated`, not `anon`, so a policy only `to anon` doesn't apply to them.

### Example

The ledger example from `format.md` compiles to this, abbreviated:

```sql
-- Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.

-- Tables
create table "public"."account" (
  "id" uuid primary key default gen_random_uuid(),
  "owner" uuid not null,
  "currency" text not null,
  "balance" numeric(18, 6) not null,
  "status" text default 'active',
  "created_at" timestamptz default now(),
  constraint "account_currency_values" check ("currency" in ('USD', 'EUR', 'GBP', 'INR')),
  constraint "account_status_values" check ("status" in ('active', 'frozen', 'closed')),
  constraint "balance_non_negative" check ("balance" >= 0),
  constraint "account_owner_currency_key" unique ("owner", "currency")
);

-- Foreign keys
alter table "public"."account" add constraint "account_owner_fkey" foreign key ("owner") references "auth"."users" ("id");

-- Access
alter table "public"."account" enable row level security;

-- Policies
create policy "owner_reads_own_accounts" on "public"."account"
  for select to authenticated
  using ("owner" = (select auth.uid()));
```

## TypeScript

One Zod schema and one type per entity, in file order:

```ts
// Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.
import { z } from "zod";

export const Account = z.object({
  id: z.string().uuid(),
  owner: z.string().uuid(),
  currency: z.enum(["USD", "EUR", "GBP", "INR"]),
  balance: decimal(18, 6),
  status: z.enum(["active", "frozen", "closed"]).nullable(),
  created_at: z.string().datetime({ offset: true }).nullable(),
});
export type Account = z.infer<typeof Account>;
```

- **Required fields** are plain. **Optional fields** are `.nullable()`, matching a column that allows `null`.
- **`decimal` and `money`** use a small generated `decimal(precision, scale)` helper, emitted only when the file needs it. It always yields a **string**, checked against the precision and scale: at most `precision - scale` digits before the point, and `scale` after.
  - **Why not just strings:** Supabase's API returns `numeric` columns as JSON numbers, and JavaScript rounds numbers past about 15 significant digits. For example, `123456789012.123456` arrives as `123456789012.12346`.
  - **So the helper accepts exact strings, plus numbers that are still exact.** A number counts as exact while `number * 10^scale` is a safe integer. Larger numbers are **rejected** with a message to select the column as text (`balance::text`), so a rounded amount is never accepted silently.
- **Zod versions:** the output only uses APIs that exist in both Zod 3.23+ and Zod 4. It's checked with Zod 3.25 and 4.6.
- **`int`** is `z.number().int()`, **`json`** is `z.unknown()`, and **`date`** is `z.string().date()`.
- **In version 0.1, declared constraints are enforced by the database only.** Mirroring them in Zod is planned, with matching names, so a failure on either side reports the same constraint name.

## Sign-in settings

`supabase/config.toml` belongs to the Supabase CLI and to you, so Svetra never writes the whole file. With an `auth` section, it sets only the keys below, in place, and keeps every other line and comment as it was.

| Key | Value |
|---|---|
| `[auth] enable_signup` | `true` for `signup: open`, `false` for `invite_only` |
| `[auth] enable_anonymous_sign_ins` | `false` |
| `[auth] minimum_password_length` | `password.min_length` |
| `[auth] password_requirements` | `password.require`, or `""` for `none` |
| `[auth.email] enabled` | `true` when `email` is in `sign_in` |
| `[auth.email] enable_confirmations` | `confirm_email` |
| `[auth.email] secure_password_change` | `true`: changing a password needs a recent sign-in |
| `[auth.mfa.totp] enroll_enabled`, `verify_enabled` | `true` when any role has `mfa: true`, otherwise `false` |
| `[auth.external.<provider>] enabled` | `true` for each OAuth provider in `sign_in`. Every other `[auth.external.*]` table already in the file gets `false` |
| `[auth.external.<provider>] client_id`, `secret` | `"env(SUPABASE_AUTH_EXTERNAL_<PROVIDER>_CLIENT_ID)"` and `"env(SUPABASE_AUTH_EXTERNAL_<PROVIDER>_SECRET)"`, so credentials never live in the file |

- **A missing key** is added at the end of its table. **A missing table** is added at the end of the file.
- **No `config.toml`:** nothing is written, and `compile` says to run `supabase init` first. The other outputs are written as usual.
- **No `auth` section:** `config.toml` isn't touched.
- **`--check`** lists every owned key whose value differs, for example `out of date: supabase/config.toml (auth.minimum_password_length is 6, svetra.yaml says 10)`.
- **The header comment isn't added** to this file, because Svetra doesn't own it.

### Second factors in SQL

For roles with `mfa: true`, `svetra.has_role` also requires the session's assurance level to be `aal2`, which Supabase sets once a person has verified an authenticator app:

```sql
where g."user_id" = (select auth.uid()) and g."role" = p_role and g."scope_id" is not distinct from p_scope
  and (g."role" not in ('admin') or coalesce((select auth.jwt() ->> 'aal'), '') = 'aal2')
```

The list holds every role with `mfa: true`. Without any, the line is left out.

## Audit

An `-- Audit` section after `-- Guards`, present only when an entity or hole has `audit: true` (docs/format.md, Audit).

```sql
create schema if not exists "svetra";
create table "svetra"."audit_log" (
  "id" bigint generated always as identity primary key,
  "at" timestamptz not null default now(),
  "actor" uuid,
  "kind" text not null check ("kind" in ('row', 'call')),
  "subject" text not null,
  "action" text not null check ("action" in ('insert', 'update', 'delete', 'call')),
  "old" jsonb,
  "new" jsonb
);
alter table "svetra"."audit_log" enable row level security;
revoke all on table "svetra"."audit_log" from public, anon, authenticated;

create function "svetra"."audit_frozen"() returns trigger language plpgsql as $svetra$
begin
  raise exception 'the audit log is append-only' using errcode = '42501';
end $svetra$;
create trigger "svetra_audit_frozen" before update or delete on "svetra"."audit_log"
  for each row execute function "svetra"."audit_frozen"();
create trigger "svetra_audit_frozen_truncate" before truncate on "svetra"."audit_log"
  for each statement execute function "svetra"."audit_frozen"();

create function "svetra"."audit_row"() returns trigger language plpgsql
  security definer set search_path = '' as $svetra$
begin
  insert into "svetra"."audit_log" ("actor", "kind", "subject", "action", "old", "new")
  values ((select auth.uid()), 'row', tg_table_name, lower(tg_op),
    case when tg_op <> 'INSERT' then to_jsonb(old) end,
    case when tg_op <> 'DELETE' then to_jsonb(new) end);
  return null;
end $svetra$;
create trigger "svetra_audit" after insert or update or delete on "public"."ledger_entry"
  for each row execute function "svetra"."audit_row"();
```

- **One generic row function**, `svetra.audit_row`, and one `svetra_audit` trigger per audited entity. It is `security definer`, so the writer needs no access to the log, and `search_path` is fixed to `''`.
- **The log is `private` in effect:** row-level security with no policy, no grants for the API roles, and a schema Supabase doesn't expose. Hole roles get no grant on it.
- **A hole with `audit: true`** gets one more statement in its `public.<name>` function, the one the app calls, before the call to the body function:

  ```sql
  insert into "svetra"."audit_log" ("actor", "kind", "subject", "action", "new")
  values ((select auth.uid()), 'call', 'transfer', 'call', jsonb_build_object('source', source, 'amount', amount));
  ```

  The wrapper is owned by the migration's role, so the hole's own role never touches the log. It runs before the body function, so the `when` guard hasn't run yet; if the guard refuses, the exception rolls the record back with everything else, and only calls that were allowed stay recorded. A hole with no inputs logs `'{}'::jsonb`.
- **Why `after` and `return null`:** the trigger records changes that went through, once every constraint and `before` trigger (such as the column guard) has passed.
- **Append-only** is the `audit_frozen` trigger. It is not a privilege: it also stops the owner.
- A document with no `audit: true` produces no change in the output.

## Holes

Each hole compiles to two functions, plus a role that holds exactly its declared access. All of it is in the SQL schema, in a `-- Holes` section after `-- Policies`.

1. **A role per hole,** `svetra_hole_<name>`, which can't log in. It gets `select` on each entity in `reads` and `writes`, and `insert`, `update` and `delete` on each entity in `writes`, nothing else, plus a permissive policy on each of those tables that lets it through row-level security. Those grants are the only thing a hole's code can touch.
   - **With `grants`,** the role also gets `select`, `insert` and `delete` on `svetra.role_grants`, and a policy that limits all three to the listed roles: `using ("role" in ('member')) with check ("role" in ('member'))`. It can give and take away those roles, for anyone, and can't see or touch any other role's grants.
2. **The body function,** `svetra_holes.<name>(p_caller, p_<input>, …)`, in a schema the API doesn't expose. It's `security definer` and owned by the hole's role, so its statements run with that role's access and no more, and it has `set search_path = ''`. Svetra writes the signature, then:
   - **the `when` guard first,** left out when there's no `when`: if the condition isn't true, it raises SQLSTATE `42501` (insufficient privilege), so a refused call looks like any other refusal. `auth.user` in the guard is `p_caller`.
   - **then each `require` condition,** in order, left out when there is none: if it isn't true (a null isn't), it raises SQLSTATE `22023` with the message `<hole>: <condition as written>`, set with `using message` so a `%` in the text is not read as a placeholder. It runs after the guard, so a refused caller never reaches it, and it holds for every caller, not only Svetra's client
   - **then the body** from `supabase/holes/<name>.sql`, verbatim

   Only the migration's role may execute it, so no caller can pass in someone else's id.
3. **The callable function,** `public.<name>`, which the app calls with `supabase.rpc('<name>', …)`. It's generated in full, with no hand-written code. It's `security definer`, so it can call the body function, passing `auth.uid()` as `p_caller` and the arguments as they came. Execute is granted to the hole's `as` roles and revoked from everyone else, so a logged-out visitor calling an `authenticated` hole gets "permission denied". Both functions revoke execute from `public`, `anon` and `authenticated` by name before granting it, because Supabase grants execute on every new function in `public` to `anon` and `authenticated` directly, which a revoke from `public` alone leaves in place.

**A body that is a whole function** (`begin … end` with no `;`), or any body whose last statement has no `;`, is refused with `SVT032`, reported against `supabase/holes/<name>.sql`, before anything is written: the function Svetra puts around it would not parse.

**The stub body** returns nothing useful and says so: `raise exception 'transfer is not written yet: edit supabase/holes/transfer.sql';`. A hole with a stub still compiles, applies and passes the access tests, because the guard runs before it.

**`--check`** compares the schema including the current bodies, so an edited body that hasn't been compiled shows up as out of date.

### Holes in TypeScript

`src/svetra.gen.ts` gets one function per hole, which validates the input with Zod, calls `rpc`, and validates the result:

```ts
export async function transfer(client: Rpc, input: TransferInput): Promise<Transaction>
```

`Rpc` is the one method it needs, `rpc(name, args)`, so the file needs no Supabase import. A Supabase client fits it.

### Holes in the access tests

For each hole:
- **Access:** a check that the hole's role can do exactly what `reads` and `writes` declare on every entity, and nothing on the others (`has_table_privilege`).
- **Role grants,** when there are roles: the hole's role has `select, insert, delete` on `svetra.role_grants` if it has `grants`, and no privilege otherwise. A hole with `grants` then tries, as its own role, to give alice each declared role: allowed for the roles it lists, denied for every other.
- **The guard,** for every person and the test rows:
  - a call with inputs that point at the `a` rows, and one with inputs that point at the `b` rows
  - each is expected to be refused (`42501`) or let through, as the evaluator works out from `when`
  - **"let through" means the guard passed,** whatever the body then does, so the check doesn't depend on hand-written code

### Scheduled holes

A hole with `kind: schedule` gets the role and the body function above, with `p_caller` always `null` and no `when` guard. It gets **no** `public` function, no entry in `src/svetra.gen.ts` and no call checks. The body function is revoked from `public`, `anon` and `authenticated` by name, and from `service_role` too when that role exists. In its place the `-- Holes` section has:

```sql
do $$ begin if to_regnamespace('cron') is null then create extension pg_cron; end if; end $$;
select cron.schedule('svetra_expire_invites', '0 3 * * *',
  $job$select "svetra_holes"."expire_invites"(null)
    where pg_try_advisory_xact_lock(hashtext('svetra_expire_invites'))$job$);
select cron.unschedule(jobid) from cron.job
  where jobname like 'svetra\_%' and jobname not in ('svetra_expire_invites');
```

- **The job** is named `svetra_<name>`. Scheduling again under the same name replaces it, so re-applying the schema is safe. It runs as the migration's role, which is the only role that can execute the body function; the body then runs as the hole's role. Times are UTC (pg_cron's `cron.timezone`).
- **The lock** makes a second run do nothing while one is still going. pg_cron never overlaps a job with itself, so it matters only for a job made by hand.
- **The cleanup** unschedules every `svetra_` job the design doesn't declare, and never a job with another name. It is emitted only when the design has a scheduled hole, so a project without one never needs pg_cron.
- **The stand-in** (`src/standin/base.sql`) has a stub `cron` schema with `job`, `schedule` and `unschedule`, so the same file applies on plain PostgreSQL.

Access tests for each scheduled hole: its role's table privileges as above; `anon`, `authenticated` and `service_role` (when it exists) can't execute `svetra_holes.<name>`; no function `<name>` exists in `public`; `cron.job` has exactly one job `svetra_<name>` with the declared schedule that calls `svetra_holes.<name>`; and, once for the file, no `svetra_` job exists that the design doesn't declare, and `cron.timezone` is UTC. The tests read `cron.job` as the migration's role. What a body does, and that pg_cron fires on time, aren't tested.

### Triggered holes

A hole with `kind: trigger` gets the role and the body function above, with the signature `svetra_holes.<name>(p_caller uuid, p_old "public"."<table>", p_new "public"."<table>")` and no `when` guard (the trigger's `WHEN` clause is the guard). Like a scheduled hole, it gets no `public` function, nothing in `src/svetra.gen.ts` and no call checks. In place of the job the `-- Holes` section has a trigger function and one trigger per event:

```sql
create function "svetra_holes"."notify_paid__fire"() returns trigger
  language plpgsql security definer set search_path = ''
  as $svetra$
begin
  if pg_trigger_depth() > 3 then
    raise exception 'notify_paid is part of a trigger loop' using errcode = '54001';
  end if;
  perform "svetra_holes"."notify_paid"((select auth.uid()),
    case when tg_op = 'INSERT' then null else old end,
    case when tg_op = 'DELETE' then null else new end);
  return null;
end
$svetra$;
revoke all on function "svetra_holes"."notify_paid__fire"() from public, anon, authenticated;
create trigger "svetra_notify_paid_update" after update on "public"."order"
  for each row when (new."status" = 'paid' and old."status" <> 'paid')
  execute function "svetra_holes"."notify_paid__fire"();
```

- **The trigger function** is owned by the migration's role and is `security definer`: that is what lets a person who can't execute anything in `svetra_holes` fire it (checked on PostgreSQL 16 and a local Supabase, [automations.md](automations.md#what-supabase-supports)). It is the only caller of the body function, which the migration's role may execute and no API role may. Both functions are revoked from `public`, `anon` and `authenticated`, and from `service_role` when that role exists.
- **One trigger per event**, named `svetra_<name>_<event>`, always `after`, `for each row`, so each can use the right row in its `WHEN`. Bare fields in `when` become `new."col"` (`old."col"` for `delete`), and `old.<field>` becomes `old."col"`. `is null` and `is not null` stand in for `== null`, as everywhere. Where the Svetra expression is `!=` the SQL is `<>`.
- **The depth limit** raises SQLSTATE `54001` when triggers nest more than three deep, a backstop for loops `SVT038` can't see.

Access tests for each trigger hole: its role's table privileges as above; `anon`, `authenticated` and `service_role` (when it exists) can't execute the body or the trigger function; no function `<name>` exists in `public`; `pg_trigger` has exactly one enabled `after`, `for each row` trigger per declared event on the declared table, each calling the trigger function, and no other `svetra_<name>_` trigger; each trigger's definition contains the compiled `when`; the body function is `security definer`, owned by the hole's role, with an empty `search_path`; the hole's role is refused an insert into an entity it doesn't write; and, where the design lets a person insert a row into the entity, inserting one as that person fires the hole. What a body does isn't tested.

## Access tests

`supabase/tests/svetra.test.sql` checks that the **database** enforces what `svetra.yaml` says, as real users. Run it against a local Supabase with `supabase test db`.

It catches what the other outputs can't:
- **Drift:** another migration adds a policy that widens access, turns row-level security off, or changes grants. `compile --check` only sees the files Svetra wrote; these tests see the database.
- **Wrong assumptions:** a rule that reads right but doesn't do what was meant, such as `as: anon` hiding public rows from signed-in people.

### Rules the tests follow

- **Never as the service key or a superuser.** Every check runs as Supabase's `anon` or `authenticated` role, with the person's id in the JWT claims. Those keys bypass row-level security, so a test run with them proves nothing.
- **Every failure is reported.** Each check is its own pgTAP test, so one broken rule doesn't hide the others. The output names the person, the action and the row, with what happened and what was expected.
- **Nothing persists.** The file runs in one transaction that ends in `rollback`, and each check also runs inside its own sub-transaction, which is undone afterwards. A check that creates or deletes a row can't affect the next one.
- **Existing data doesn't matter.** Checks only touch the test rows, by primary key, so seed data in the database neither breaks nor hides a result.
- **Expected results come from `svetra.yaml`, not from the generated SQL.** The test generator evaluates each rule itself, with SQL's `null` semantics. A bug in the SQL compiler, or a hand edit to the database, shows up as a disagreement.

### The people

| Person | Signed in | Holds |
|---|---|---|
| `anon` | No | |
| `alice` | Yes | Owns the `a` rows: every `user` field on them is alice |
| `bob` | Yes | Owns the `b` rows |
| `carol` | Yes, **with a second factor** | Nothing: no rows, no role. Anyone can add a second factor to their own account, so a rule open to every signed-in person, or a role check that forgets who holds the role, shows up as carol getting something |
| One per global role, named after it, e.g. `admin` | Yes | That role. Owns nothing |
| One per scoped role, e.g. `staff at Location a` | Yes | That role for the scope entity's `a` row. Owns nothing |
| One per role with `mfa: true`, e.g. `admin without a second factor` | Yes | The same grant, in a session without a second factor. Gets only what any signed-in person gets |
| One per role, `alice who is also admin` or `alice who is also staff at Location b` | Yes | alice (she owns the `a` rows) **and** the role; a scoped role is held for the scope entity's `b` row, the one her own rows don't point at. This is an owner who is also a role holder, the combination where two update policies can be combined (PostgreSQL ORs their `check`s independently). The grant is given by the database owner just before each of her checks and undone with it, so no other check sees it. Only added when an entity has a `user` field; not shown in `svetra view` |

Ids are fixed UUIDs: `5e7a0000-0000-4000-8000-0000000000NN`, where `NN` is the person's position in the table above, starting at `01` for alice. `anon` has no id.

### The test rows

Each entity that the API can reach gets two stored rows, `a` and `b`, plus two candidate rows for creating, `c` (like `a`) and `d` (like `b`).

- **`a` and `b` differ in every field,** so a rule that compares a field sees both outcomes. `c` and `d` keep the owners and links of `a` and `b`, and differ from them elsewhere, so creating one doesn't collide with a `unique` rule:
  - `user` fields: alice on `a` and `c`, bob on `b` and `d`
  - `ref` fields: the first ref to each entity points at the target's `a` row on `a` and `c`, and its `b` row on `b` and `d`. A second ref to the same entity points at the other row, so `source != destination` holds
  - enums: the values in turn, `a` getting the first, `b` the second, `c` the third and `d` the fourth, wrapping around when there are fewer
  - `bool`: `true` on `a` and `c`, `false` on `b` and `d`
  - other types: distinct values per row, e.g. `1` to `4` for numbers, `'svetra a'` to `'svetra d'` for text, and `2030-01-01` to `2030-01-04` for dates and timestamps
- **A `user` primary key** can't follow the rule for other `user` fields, because the candidate rows `c` and `d` would then repeat the keys of `a` and `b` (alice and bob) and collide with the rows the tests already stored. On such an entity the four rows are keyed by four different people: `a` is alice, `b` is bob, `c` is carol and `d` is a fourth person, `5e7a0000-0000-4000-8000-000000000fff`, who is added to `auth.users` for this and has no checks of their own. Creating `c` is then something only carol can be allowed to do, and creating `d` something nobody signed in as one of the people above can. Every other `user` field on the entity keeps its usual owners.
- **Primary keys:** `uuid` keys are `5e7a0000-0000-4000-8001-EEEE0000000R`, where `EEEE` is the entity's position in the file and `R` is `a` to `d`. `text` keys are `'svetra a'` to `'svetra d'`, and `int` keys are `2000000001` to `2000000004`.
- **Rows are inserted as the database owner, as test data,** in reference order, each as its own test. If a declared constraint rejects a generated value, that test fails with the database's message, naming the entity and row.
- **Role grants** are inserted into `svetra.role_grants` the same way.

### The checks

For every reachable entity and every person:

| Check | How it runs | Allowed when |
|---|---|---|
| see `a`, see `b` | `select` the row by primary key | Some `select` rule for the person's role holds on the row |
| change `a`, change `b` | `update` the row, setting its primary key to itself | Some `select` rule **and** some `update` rule hold on the row. Postgres applies `select` rules to an update that finds rows with `where` |
| delete `a`, delete `b` | `delete` the row by primary key | Some `select` rule **and** some `delete` rule hold on the row, and no `restrict` reference blocks it (see below). When the rules allow it but a reference blocks it, the expected result is `blocked` |
| create `c`, create `d` | `insert` the candidate row | Some `insert` rule holds on the new row |
| change who owns `a` or `b`, or what it belongs to | `update` one `user` or `ref` field of the row: a `user` field to the person themselves (or, on their own row, to the other owner), a `ref` to the target's other row. Signed-in people only | The row can be changed (as above), **and** some `update` rule and some `select` rule hold on the row as the update leaves it. This is how a person could take a row over, give it away, or move it out of their scope |

| change a field a rule with a `check` reads, to each value | `update` that one `enum` or `bool` field to each of its values (each enum value, or `true` and `false`), skipping the value the row already has | The row can be changed from where it is (an update rule's `when` holds, and some `select` rule), **and** the row as the update leaves it passes an update rule's `check` and a `select` rule. This is how a draft becomes submitted and nothing else. Generated only for an entity with a policy that has a `check`, so a design without one gets none |

- **Rules combine as PostgreSQL combines them.** Some permissive policy must hold, and every restrictive policy must hold too; null counts as not holding. For an update, the old row is read against the update policies' `when`, and the new row against their `check` (`when` when there is none) and against the select policies. The two sides combine **independently across policies**: the old row may pass one policy and the new row another (checked on PostgreSQL 16, docs/update-check.md). `svetra validate` warns (`SVT034`) when a check in the tests exposes such a combination.
- **Rules that apply to a person:** `anon` gets rules with `as: anon` or `as: anyone`. Everyone signed in gets `as: authenticated` (the default) or `as: anyone`.
- **Deleting a referenced row** (`on_delete`, [format.md](format.md#deleting-a-referenced-row)): the stored rows point at each other as the test rows say (the `a` row at the target's `a` row, the `b` row at its `b` row). A delete the rules allow is expected to be `blocked` when some stored row still points at the deleted one through a `restrict` field, found through every `cascade` on the way: deleting the row also deletes the rows that cascade from it, and those rows' own `restrict` references count too, except those from rows the same delete removes anyway (a row pointing at itself, or a row the cascade deletes). `set_null` never blocks. Whether it blocks comes from the `on_delete` options in `svetra.yaml`, never from the generated foreign keys, so a key that was changed by hand shows up as a disagreement. A delete the rules deny stays `denied` whatever points at the row, because row-level security hides the row before any key is looked at. The checks don't look at the rows a cascade removes or a `set_null` clears: they are undone with the check.
- **Private entities** get two checks for `anon` and for `alice`: see `a` and create `c`. Both must be denied, because the API has no grants on them.
- **Fields a declared constraint names,** and a field alone in a `unique` rule when the new value is another row's, get no change-who-owns check, because the database could reject the value for that reason instead.
- **A `user` primary key** also gets change-who-owns checks on the key itself. The key can only be changed to one no stored row holds, because the other stored row's key fails on the primary key whatever the rules say, so the checks aim at keys nobody holds: **take it over** (a signed-in person who holds no row, such as carol or a role holder, sets the key of `a` and of `b` to themselves) and **give it away** (every signed-in person sets the key of `a` and of `b` to the fourth person, who holds no row). The first is not generated for alice and bob, whose own keys are stored. Both are allowed under the same rule as the other change-who-owns checks, computed from the policies with the key as the update leaves it. An entity whose key is named by a declared constraint, or whose stored row another stored row points at (the foreign key would refuse the change), gets none. Without them, `using (true)` or `with check (true)` on the update policy of a profile table keyed by the person went unnoticed.
- **Owner and reference changed together:** each signed-in person, for each stored row, also gets one update that changes a `user` field and a `ref` field at once (take the row over and point it somewhere else). Each alone can be refused while the pair is allowed, because the new row can be seen through one policy while another policy's `check` lets the update through; only the pair shows a loosened `check`.
- **Roles:** when there are roles, `alice can't give herself the <role> role` inserts a grant for herself into `svetra.role_grants`, which must be denied.
- **Holes:** besides their table privileges and who gets past `when`, `anon` and signed-in people must be able to run the hole's public function exactly as its `as` says, and must never be able to run the function inside `svetra_holes` directly, because that one takes the caller's id as an argument.
- **Results** are `allowed` when the statement touches the row, and `denied` when it touches nothing or is refused by row-level security (SQLSTATE `42501`). `blocked` is a delete refused by a foreign key (SQLSTATE `23503`, "update or delete on table ... violates foreign key constraint"). Anything else, such as a constraint error, is reported as `error <sqlstate>: <message>`, which never matches an expected result.

**Test names** read as sentences: `ok 12 - bob can't see Booking a`, `ok 31 - staff at Location a can change Booking a`, `staff at Location a can't point the location of Booking a at Location b`.

### Example

For the bookings app (two entities, two roles), people are `anon`, `alice`, `bob`, `carol`, `admin`, `staff at Location a`, `alice who is also admin` and `alice who is also staff at Location b`. Each gets 8 checks on Booking and 8 on Location (128), the seven signed-in people each get 4 change-who-owns checks on Booking (28) and one that changes the customer and the location together (14), and alice can't give herself the admin role (1): 171 checks, plus 7 test-data tests. A policy added by hand, such as `create policy leak on booking for select to authenticated using (true)`, makes `alice can't see Booking b`, `bob can't see Booking a`, `carol can't see Booking a`, `carol can't see Booking b` and `staff at Location a can't see Booking b` fail.

**How these checks were chosen:** a mutation study (`scripts/mutate.py`) breaks the deployed database in 197 ways and counts what the checks catch. carol, the change-who-owns checks and the hole function checks each come from a kind of break the earlier checks missed. So do the owner who is also a role holder and the owner-and-reference change in one update: a Z3 model of the bookings policies showed that loosening one of two update policies went unnoticed without them (four real gaps in both rounds).

### Limits in version 0.1

- **Generated values can break declared constraints,** for example `ends > starts` when both get the same kind of value. The test-data test reports it. Choosing values that satisfy constraints is planned.
- **Holes aren't tested,** because their bodies are written by the agent. Grants and rules on the tables they touch are.
- **Times compared with text** are read the way Postgres reads them when the text is an ISO time: `YYYY-MM-DD`, optionally with `T` or a space and `HH:MM[:SS]`, optionally ending in `Z` or `+00:00`, all in UTC. A `date` compared with such text ignores the time of day. Any other text, such as `'now'`, can't be evaluated ahead of time, so each check it could decide becomes a pgTAP skip that says so, never a guess.
- **One connection runs every check.** Each check switches role and claims inside its own sub-transaction, which resets both on exit. Separate connections per person are planned.

## Not in version 0.1

- Other hole kinds (scheduled jobs, triggers, webhooks) and holes that call external services: planned for M4b, as Supabase Edge Functions.
- Configurable output paths.
- Migrations: Supabase generates them from the declarative schema with `supabase db diff`.
- Foreign-key options other than `on_delete` (`on update`, deferrable keys), and `on_delete` on a `user` field.

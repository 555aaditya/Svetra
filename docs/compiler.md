# `svetra compile`, version 0.1

This document specifies what the compiler produces from a valid `svetra.yaml`. The format itself is specified in [`format.md`](format.md). When the compiler and this document disagree, that's a bug in one of them.

## Command

```sh
svetra compile [FILE] [--check]
```

- **`FILE`** defaults to `./svetra.yaml`. Paths in the output are relative to the folder `FILE` is in.
- **The compiler validates first.** If `svetra validate` would report any error, nothing is written, and the diagnostics are printed with exit code `1`.
- **`--check`** writes nothing. It exits `0` if every output file already matches what the compiler would write, and `1` otherwise, listing the files that differ. CI uses it to catch hand edits and stale output.
- **Exit codes:**
  - `0`: written, or up to date with `--check`
  - `1`: validation errors, or stale files with `--check`
  - `2`: usage error

## Outputs

| File | Contents | Consumed by |
|---|---|---|
| `supabase/schemas/svetra.sql` | Tables, constraints, foreign keys, indexes, row-level security and policies | Supabase's [declarative schemas](https://supabase.com/docs/guides/local-development/declarative-database-schemas): `supabase db diff` turns it into migrations |
| `src/svetra.gen.ts` | TypeScript types and Zod validators, one per entity | The React app |

Version 0.1 doesn't make these paths configurable.

**Every file starts with this header:**

```
-- Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.
```

It's `//` instead of `--` in TypeScript. The **revision** is the first 12 hex digits of the SHA-256 of the `svetra.yaml` bytes. `svetra check` will later use it to spot generated files that are older than the graph.

## Determinism

The same `svetra.yaml` and the same compiler version always produce byte-identical files:
- Output order is fixed: the sections below appear in order, and entities and policies within a section appear in file order.
- No timestamps, no randomness, and no hash-map iteration order.
- Files end with a single newline.

## SQL

### Names

- **Every identifier is double-quoted.** Entity names such as `Order` and `User` become reserved words in SQL (`order`, `user`), and quoting makes them safe.
- **The table name is the entity name in snake_case,** in the `public` schema: `LedgerEntry` becomes `"public"."ledger_entry"`.
- **Column names are the field names.**
- **Generated constraint and index names:**

| Object | Name |
|---|---|
| Enum check | `<table>_<field>_values` |
| Declared constraint | its own name, from `constraints` |
| Unique constraint | `<table>_<col>_<col>_key` |
| Foreign key | `<table>_<field>_fkey` |
| Index | `<table>_<col>_<col>_idx` |

### Sections, in order

1. **Tables.** `create table` for every entity: columns, primary key, `not null`, defaults, enum checks, declared constraints and unique constraints. No foreign keys here.
2. **Foreign keys.** `alter table ... add constraint ... foreign key` for every `ref` and `user` field. Adding them after the tables means entities that reference each other in a cycle still work.
3. **Indexes.** Declared `indexes`, plus one index for each reference field that no index or unique constraint already leads with (rule SVT010).
4. **Access.**
   - `alter table ... enable row level security` for **every** table, so a table with no policy denies everyone.
   - For `private` entities, also `revoke all ... from anon, authenticated`, so the generated API can't reach them at all.
5. **Policies.** One `create policy` for each policy and action.

When the file declares `roles`, a **Roles** section comes before Access:

```sql
create schema if not exists "svetra";
create table "svetra"."role_grants" (
  "user_id" uuid not null references "auth"."users" ("id") on delete cascade,
  "role" text not null check ("role" in ('admin', 'staff')),
  "scope_id" uuid,
  constraint "role_grants_key" unique nulls not distinct ("user_id", "role", "scope_id")
);
alter table "svetra"."role_grants" enable row level security;

create function "svetra"."has_role"(p_role text, p_scope uuid default null)
  returns boolean language sql stable security definer set search_path = ''
  as $$ select exists (
    select 1 from "svetra"."role_grants" g
    where g."user_id" = (select auth.uid()) and g."role" = p_role and g."scope_id" is not distinct from p_scope
  ) $$;
revoke all on function "svetra"."has_role"(text, uuid) from public;
grant usage on schema "svetra" to anon, authenticated;
grant execute on function "svetra"."has_role"(text, uuid) to anon, authenticated;
```

- **`role_grants` is unreachable from the API.** The `svetra` schema isn't exposed by Supabase, the table has no grants for `anon` or `authenticated`, and it has row-level security with no policies.
- **`has_role` is `security definer`:** it reads `role_grants` as its owner. A policy calling it never runs another table's policies, which avoids the recursion problem that policies referencing each other can cause. `search_path` is fixed to `''`, so it can't be hijacked.
- `unique nulls not distinct` needs PostgreSQL 15 or later, which Supabase uses.

### Columns

| Field | Column |
|---|---|
| `primary: true` with `uuid` | `uuid primary key default gen_random_uuid()` |
| `primary: true` with another type | `<type> primary key` |
| `required: true` | `not null` |
| `default: x` | `default <literal>` |
| `auto: now` | `default now()` |
| `enum` | `text`, plus `constraint "<table>_<field>_values" check ("<field>" in ('a', 'b'))` |
| `ref` | `uuid`, plus a foreign key to the referenced entity's primary field |
| `user` | `uuid`, plus a foreign key to `"auth"."users" ("id")` |

The other type mappings are in [`format.md`](format.md#types).

Foreign keys use PostgreSQL's default `on delete no action`, so a referenced row can't be deleted while something still points at it. Cascading deletes come later, as an explicit option.

### Expressions in SQL

Constraints and policy conditions translate like this:

| Expression | SQL |
|---|---|
| `a == b`, `a != b` | `a = b`, `a <> b` |
| `x == null`, `x != null` | `x is null`, `x is not null` |
| `and`, `or`, `not` | `and`, `or`, `not`, with parentheses kept |
| `x in ['a', 'b']` | `x in ('a', 'b')` |
| `'it''s'` | `'it''s'`; single quotes are escaped by doubling |
| A field `f` | `"f"` |
| `auth.user` | `(select auth.uid())`, the form Supabase recommends, which Postgres evaluates once per query instead of once per row |
| `has_role('admin')` | `(select "svetra"."has_role"('admin'))`, evaluated once per query |
| `has_role('staff', location)` | `"svetra"."has_role"('staff', "location")`, evaluated per row |
| `ref.field` (policies only) | `(select t."field" from "public"."<target>" t where t."<pk>" = "<table>"."ref")`, a scalar subquery on the referenced row's primary key |

### Policies

- `select` and `delete` put the condition in `using (...)`.
- `insert` puts it in `with check (...)`.
- `update` puts it in both.
- A policy with one action keeps its name. With more than one action, each gets `<policy>_<action>`.
- The default becomes `to authenticated`. `as: anyone` becomes `to anon, authenticated`, and `as: anon` becomes `to anon`. In Supabase, signed-in people run as `authenticated`, not `anon`, so a policy only `to anon` doesn't apply to them.

### Example

The ledger example from `format.md` compiles to this, abbreviated:

```sql
-- Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.

-- Tables
create table "public"."account" (
  "id" uuid primary key default gen_random_uuid(),
  "owner" uuid not null,
  "currency" text not null,
  "balance" numeric(18, 6) not null,
  "status" text default 'active',
  "created_at" timestamptz default now(),
  constraint "account_currency_values" check ("currency" in ('USD', 'EUR', 'GBP', 'INR')),
  constraint "account_status_values" check ("status" in ('active', 'frozen', 'closed')),
  constraint "balance_non_negative" check ("balance" >= 0),
  constraint "account_owner_currency_key" unique ("owner", "currency")
);

-- Foreign keys
alter table "public"."account" add constraint "account_owner_fkey" foreign key ("owner") references "auth"."users" ("id");

-- Access
alter table "public"."account" enable row level security;

-- Policies
create policy "owner_reads_own_accounts" on "public"."account"
  for select to authenticated
  using ("owner" = (select auth.uid()));
```

## TypeScript

One Zod schema and one type per entity, in file order:

```ts
// Generated by svetra 0.1.0 from svetra.yaml (revision 3f9a1c2e8b7d). Do not edit.
import { z } from "zod";

export const Account = z.object({
  id: z.string().uuid(),
  owner: z.string().uuid(),
  currency: z.enum(["USD", "EUR", "GBP", "INR"]),
  balance: decimal(18, 6),
  status: z.enum(["active", "frozen", "closed"]).nullable(),
  created_at: z.string().datetime({ offset: true }).nullable(),
});
export type Account = z.infer<typeof Account>;
```

- **Required fields** are plain. **Optional fields** are `.nullable()`, matching a column that allows `null`.
- **`decimal` and `money`** use a small generated `decimal(precision, scale)` helper, emitted only when the file needs it. It always yields a **string**, checked against the precision and scale: at most `precision - scale` digits before the point, and `scale` after.
  - **Why not just strings:** Supabase's API returns `numeric` columns as JSON numbers, and JavaScript rounds numbers past about 15 significant digits. For example, `123456789012.123456` arrives as `123456789012.12346`.
  - **So the helper accepts exact strings, plus numbers that are still exact.** A number counts as exact while `number * 10^scale` is a safe integer. Larger numbers are **rejected** with a message to select the column as text (`balance::text`), so a rounded amount is never accepted silently.
- **Zod versions:** the output only uses APIs that exist in both Zod 3.23+ and Zod 4. It's checked with Zod 3.25 and 4.6.
- **`int`** is `z.number().int()`, **`json`** is `z.unknown()`, and **`date`** is `z.string().date()`.
- **In version 0.1, declared constraints are enforced by the database only.** Mirroring them in Zod is planned, with matching names, so a failure on either side reports the same constraint name.

## Not in version 0.1

- Hole signature files: planned with the agent interface, M4.
- Configurable output paths.
- Migrations: Supabase generates them from the declarative schema with `supabase db diff`.
- Cascading deletes, and other foreign-key options.
